4가로 목록은 높이를 아무도 안 정해 준다

세로 목록은 부모가 높이를 준다. 가로 목록은 "위아래로 얼마나 차지할지"를 아무도 모른다 → 에러가 난다.

✗ Column 안에 바로 가로 ListView
✓ SizedBox로 높이를 정해 준다
카드 너비도 같은 이유로 직접 정한다 — MovieCard(width: 136). 세로 목록에서는 둘 다 신경 쓸 일이 없다.

5childAspectRatio = 가로 ÷ 세로

칸의 모양(비율)만 정한다. 실제 크기는 화면 너비에 맞춰 따라온다. 값이 작을수록 세로로 길어진다.

제목이 잘린다
포스터는 보통 2 : 3 → 약 0.67
여기에 제목·장르 두 줄이 더 붙는다
→ 그래서 0.67보다 작은 값이 필요하다
글자가 잘리면? 값을 더 줄인다. (0.7 → 0.6)

커넥션 풀 —
연결을 미리 뚫어 두고 빌려 쓴다

DB에 "연결하는 시간"이 정작 "쿼리 실행 시간"보다 훨씬 길다. 이 낭비를 없애는 게 커넥션 풀이다.

1요청마다 새로 연결하면 무슨 일이 생기나

DB 연결 한 번은 TCP 연결 → 로그인 인증 → 세션 준비를 거친다. 여기에 수십 ms가 든다. 정작 쿼리는 1ms면 끝난다.

핵심 — 풀은 쿼리를 빠르게 만드는 게 아니다. 연결 준비 시간을 요청 경로에서 빼는 것이다.

2동작 방식

서버가 켜지면 연결을 몇 개 만들어 바구니에 담아 둔다. 요청이 오면 빌려 쓰고 반드시 돌려준다.

설정은 거의 없다
Spring이 대신 만들어 준다

풀을 직접 만들 일은 없다. 대신 언제 만들어지는지와 어떻게 관리되는지는 알아야 한다.

3Spring은 자동이다

Spring Boot에는 HikariCP라는 풀이 이미 들어 있다. 아래 설정만 쓰면 풀이 저절로 만들어진다. (NestJS는 mysql2의 createPool을 직접 조립한다)

# application.yml — Spring은 이게 전부다
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/book_rental
    username: ${DB_USER:root}
    password: ${DB_PASSWORD:}
우리가 쓴 JdbcTemplate은 풀에서 빌리고 → 쿼리하고 → 반납까지 알아서 한다. 그래서 Repository에서 연결을 직접 열 일이 없다.

4기동 로그에 Hikari가 없다고 실패가 아니다

풀은 서버가 켜질 때가 아니라 첫 쿼리가 필요할 때 만들어진다(lazy 초기화).
